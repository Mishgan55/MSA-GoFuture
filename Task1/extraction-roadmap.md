# Очерёдность выделения сервисов и годовой план декомпозиции

## Контекст

Неправильный порядок выделения может превратить микросервисы в распределённый монолит. Поэтому приоритет определяется четырьмя факторами:

1. **независимость домена** — насколько мало он связан с транзакциями монолита;
2. **бизнес-эффект** — влияние на масштабирование и time-to-market;
3. **технический риск** — объём данных, консистентность, интеграции;
4. **подготовленность платформы** — наличие observability, CI/CD, event backbone и IAM.

## Порядок выделения

### Этап 0. Фундамент и стабилизация — месяцы 1–2

**Состав работ:**

- внедрить API Gateway перед монолитом;
- стандартизировать OIDC/IAM и service accounts;
- выстроить CI/CD для независимых сервисов;
- внедрить OpenTelemetry, централизованные логи, dashboards и SLO;
- развернуть Kafka, Schema Registry и transactional outbox connector;
- разделить монолитную БД логически: зафиксировать владельцев таблиц и запретить новые cross-domain joins;
- внедрить feature flags и механизмы dark launch/canary.

**Почему первым:** без этого этапа распределённую систему невозможно безопасно эксплуатировать. Именно он даёт снижение инцидентов и уменьшение MTTR ещё до массовой декомпозиции.

### Волна 1. Notification Service и Geography Service — месяцы 3–4

**Notification первым, потому что:**

- понятные входные события и внешние адаптеры;
- низкий риск нарушить финансовую или заказную консистентность;
- быстрый результат для команды и проверка шаблонов event-driven интеграции.

**Geography затем, потому что:**

- естественный bounded context: зоны, маршруты, ETA, провайдеры карт;
- высокая ценность для динамического ценообразования и региональной локализации;
- относительно слабая связанность с финансовыми операциями.

**Результат:** отключение push/картографической логики из монолита, появление первых self-contained сервисов и контрактов.

### Волна 2. Driver Service и Pricing Service — месяцы 5–6

**Driver выделяется раньше ядра Booking, потому что:**

- location/availability — самый высокочастотный write workload;
- независимое масштабирование напрямую снижает нагрузку на монолит;
- данные водителя имеют очевидного владельца.

**Pricing выделяется вслед за Driver, потому что:**

- ему требуются потоки спроса/предложения и зоны, которые уже появляются после Geography/Driver;
- динамическое ценообразование — ключевая бизнес-цель;
- домен может развиваться независимо при наличии quote API и pricing events.

**Результат:** устранение главных горячих точек масштабирования; подготовка базы для оптимизации распределения водителей.

### Волна 3. Payments Service и Fraud Service — месяцы 7–8

**Payments выделяется после платформенной стабилизации, потому что:**

- требует строгой консистентности, auditability и безопасности;
- ошибки в этом домене имеют прямые финансовые последствия;
- к этому моменту уже должны быть готовы outbox, idempotency и observability.

**Fraud выделяется рядом с Payments, потому что:**

- должен получать booking/payment events;
- работает по модели scoring/decision и не обязан находиться в hot path каждой операции;
- позволяет вынести быстро меняющиеся правила из transactional core.

**Результат:** изоляция регулируемого финансового домена, прозрачный ledger и независимое развитие антифрод-правил.

### Волна 4. Booking Service — месяцы 9–10

**Booking выделяется позже остальных, потому что:**

- это наиболее связанный и критичный домен;
- он зависит от уже выделенных Driver, Pricing, Payments и Fraud;
- преждевременное выделение привело бы к массовым синхронным вызовам обратно в монолит.

**Состав выделения:**

1. выделить read models активных поездок;
2. вынести state machine и saga orchestration;
3. перенести offer/matching lifecycle;
4. перенести cancellation/refund orchestration;
5. закрыть прямое использование таблиц монолита.

**Результат:** монолит перестаёт быть владельцем активной поездки.

### Волна 5. Analytics, Partner API и вывод монолита — месяцы 11–12

- Analytics перестраивается как downstream consumer событийной платформы.
- Выделяется Partner/Open API для самообслуживания внешних разработчиков.
- Корпоративный портал переводится на новые public API.
- Legacy Django остаётся только как временный фасад/архивный read-only контур и затем выводится.

## Календарный план

| Период | Основной результат | Метрики выхода |
|---|---|---|
| Месяцы 1–2 | Стабилизация, platform foundation, API Gateway, Kafka, observability | -70% инцидентов, MTTR ≤ 1 часа, покрытие критичных метрик 100% |
| Месяцы 3–4 | Notification и Geography в production | За сервисами закреплены данные, монолит не вызывает внешних push/map-провайдеров напрямую |
| Месяцы 5–6 | Driver Location/Availability и Pricing в production | 200k+ конкурентных поездок в нагрузочном тесте, независимый autoscaling location/pricing |
| Месяцы 7–8 | Payments и Fraud в production | Идемпотентные платежи, audit trail, payment success observability, fraud decision latency в пределах SLA |
| Месяцы 9–10 | Booking core в production | Активные поездки полностью управляются новым Booking Service; Saga покрывает failure scenarios |
| Месяцы 11–12 | Analytics/Partner API, вывод legacy | 500k+ конкурентных поездок в тесте, функции выпускаются до 2 недель, legacy business code decommissioned |

## Логика очерёдности одной строкой

Сначала создаётся управляемая платформа, затем выделяются наименее рискованные домены, после этого — главные источники нагрузки, затем финансово критичные домены и только в конце — ядро заказа, которое опирается на уже существующие сервисы.
