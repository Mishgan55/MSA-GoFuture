# Обоснование выбора регионов развёртывания

## Контекст

Текущая инфраструктура исторически связана с Yandex Cloud, но для глобальной экспансии требуется присутствие рядом с пользователями Юго-Восточной Азии и Южной Америки. В описании текущего ландшафта уже используются AWS-термины EC2/ELB/ALB, поэтому целевым глобальным провайдером выбирается AWS. Yandex Cloud может оставаться временным контуром для legacy/текущих рынков, но не является ограничением целевой архитектуры.

AWS выбран как основной глобальный провайдер потому что:

- имеет зрелые регионы в Юго-Восточной Азии и Южной Америке;
- предоставляет managed building blocks: multi-AZ networking, ALB/NLB, Route53, KMS, WAF, Shield, Aurora/RDS, MSK, S3;
- упрощает единообразный infrastructure as code и regional cell template;
- позволяет при необходимости использовать local/partner-controlled интеграции для регулируемых стран.

## Выбранные регионы

| Регион | AWS region | Роль | Обоснование |
|---|---|---|---|
| **Сингапур** | `ap-southeast-1` | Основной SEA hub | Низкая задержка для Сингапура, Малайзии, Таиланда, Вьетнама, Филиппин; зрелая сетевая инфраструктура; удобная точка для региональных интеграций |
| **Джакарта** | `ap-southeast-3` | Индонезийская compliance/cell | Индонезия — крупный рынок SEA с требованиями локализации и высокой чувствительностью к резидентности данных; локальный регион снижает latency и регуляторный риск |
| **Сан-Паулу** | `sa-east-1` | South America hub | Основной регион AWS в Южной Америке; низкая задержка для Бразилии и приемлемая для соседних стран; локальные платёжные интеграции и LGPD-friendly архитектура |
| **Франкфурт** | `eu-central-1` | Глобальный control plane/EMEA expansion/DR analytics | Нейтральная площадка для глобальных сервисов управления, аналитики и потенциального европейского расширения; не участвует в hot path поездки SEA/SA |

Итого: четыре production-региона, из которых как минимум три являются пользовательскими региональными ячейками или полноценными площадками развёртывания.

## Почему не один азиатский регион

Сингапур покрывает значительную часть SEA, но Индонезия является стратегически большим рынком и может требовать локальной обработки данных. Попытка обслуживать её только из Сингапура повышает latency и регуляторную неопределённость. Поэтому Джакарта выделена как отдельная ячейка, а Сингапур остаётся региональным хабом.

## Почему Сан-Паулу для Южной Америки

- единственный зрелый AWS-регион на континенте с широким набором сервисов;
- Бразилия — крупнейший рынок региона и вероятная точка входа;
- для Чили, Аргентины, Колумбии и Перу задержка из Сан-Паулу значительно ниже, чем из Северной Америки или Европы;
- при дальнейшей экспансии можно добавить edge locations или новые локальные ячейки без изменения архитектурного шаблона.

## Роль Франкфурта

Франкфурт не обязан обслуживать активные поездки SEA/SA. Он используется для:

- глобального control plane;
- centralized security/audit aggregation;
- обезличенной глобальной аналитики;
- каталога конфигураций и партнёрских метаданных, если это не нарушает резидентность;
- потенциального расширения в Европу.

Критичные пользовательские операции не должны синхронно зависеть от Франкфурта. Если control plane недоступен, региональные ячейки продолжают работать на последней известной конфигурации.

## Модель ячеек

Каждая ячейка включает:

- API Gateway/WAF/ALB;
- Booking, Driver, Pricing, Payments, Notification, Geography, Fraud;
- Kafka/Flink для hot path;
- PostgreSQL/Redis/ClickHouse regional storage;
- observability agents и локальные alerts;
- интеграции локальных PSP/map/push-провайдеров.

Глобально разделяются только:

- IAM federation/control plane;
- deployment registry и CI/CD control plane;
- конфигурация и feature flag distribution;
- обезличенная аналитика;
- audit/security aggregation;
- партнёрский каталог в допустимом объёме.

## Поэтапное внедрение регионов

1. **Фаза 1:** Сингапур и Сан-Паулу как первые пользовательские ячейки.
2. **Фаза 2:** Франкфурт как глобальный control plane/аналитический hub и резерв для нечувствительных данных.
3. **Фаза 3:** Джакарта как отдельная compliance-ячейка при выходе на индонезийский рынок.
4. **Фаза 4:** добавление локальных ячеек по шаблону при входе в страны с жёсткой резидентностью.

## Ограничения и риски

- В некоторых странах даже AWS local region может не закрывать все регуляторные требования; тогда используется локальный провайдер или dedicated partner-controlled deployment через тот же cell template.
- Развёртывание полноценной ячейки дорого для малого рынка. Для нового рынка допускается lightweight cell с shared non-critical компонентами, но critical services остаются региональными.
- Наличие четырёх регионов не гарантирует 99,99% само по себе: требуется отсутствие глобальных синхронных зависимостей и регулярные failover drills.
