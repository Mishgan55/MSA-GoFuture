# Механизмы обеспечения обратной совместимости

## Контекст

Мобильные приложения, корпоративный портал и партнёрские интеграции не могут обновляться одновременно с backend. Кроме того, часть сценариев временно исполняется монолитом, а часть — новыми сервисами. Поэтому обратная совместимость является обязательным архитектурным требованием, а не побочным эффектом реализации.

## Решение

### 1. Единая точка входа и routing facade

- API Gateway принимает все существующие публичные endpoint'ы монолита.
- Маршрутизация выполняется по path, version, user segment, region и feature flag.
- Старый endpoint может быть проксирован в монолит, затем — в сервис с тем же внешним контрактом.
- Для новых возможностей создаются версии `/v2`, но старые `/v1` сохраняются минимум на два major-релиза мобильных приложений.

### 2. Anti-corruption layer

Между монолитом и новыми сервисами вводится адаптер, который:

- переводит legacy DTO в доменные контракты;
- скрывает старую модель данных;
- преобразует legacy ошибки в стандартный problem+json формат;
- запрещает проникновение legacy-терминов и идентификаторов в новые домены.

ACL живёт ограниченное время и удаляется после завершения миграции соответствующего домена.

### 3. Версионирование API и событий

**API:**

- semver для внутренних API и явные версии путей для внешних;
- additive-only изменения внутри одной major-версии;
- deprecation headers и документированный sunset window;
- consumer-driven contract tests для мобильных приложений и корпоративного портала.

**События:**

- CloudEvents envelope;
- Avro/Protobuf schema в Schema Registry;
- backward/forward compatible изменения по умолчанию;
- breaking change только через новый event type или новую major-версию топика.

### 4. Expand/contract миграции схемы

Для каждой БД применяется безопасный жизненный цикл изменений:

1. **Expand:** добавить новые колонки/таблицы/индексы, не удаляя старые.
2. **Migrate:** перенести данные и включить dual-write/CDC там, где это необходимо.
3. **Switch:** перевести чтение/запись на новый сервис.
4. **Contract:** удалить устаревшие поля и код после подтверждённого отсутствия использования.

### 5. Dual-run, shadow read и dark launch

Для критичных операций используются поэтапные проверки:

- **shadow read:** новый сервис читает события/данные, но не влияет на ответ пользователю;
- **comparison job:** сравнение ответов монолита и сервиса по выборке запросов;
- **dark launch:** включение для внутренних пользователей/одного города;
- **canary:** 1–5–25–50–100% трафика;
- **instant rollback:** возврат feature flag без повторного деплоя.

### 6. Идемпотентность и повторная обработка

- Каждый mutating endpoint принимает `Idempotency-Key` для пользовательских операций.
- Kafka consumers хранят `event_id`/`command_id` в inbox-таблице.
- Повторные доставки не создают дубли платежей, уведомлений и изменений состояния заказа.
- Внешние провайдеры вызываются через адаптеры с safe retry policy.

### 7. Согласование legacy и новых идентификаторов

На переходном этапе:

- сохраняются mapping-таблицы `legacy_id <-> domain_id`;
- внешние клиенты продолжают использовать старые идентификаторы;
- новые идентификаторы добавляются в ответы как дополнительные поля;
- после миграции старый идентификатор объявляется deprecated.

### 8. Совместимость мобильных приложений

- Backend не требует force update для перехода на микросервисы.
- Неизвестные поля игнорируются клиентами; backend добавляет только additive fields.
- Для feature rollout используется remote config.
- WebSocket/push fallback сохраняется до отдельного клиентского релиза.

## Альтернативы

| Альтернатива | Почему не выбрана |
|---|---|
| Одномоментное обновление backend и клиентов | Невозможно контролировать обновление нативных приложений у всех пользователей |
| Отдельный API для каждого клиента | Размножает контракты и усиливает рассинхронизацию |
| Прямая синхронная интеграция сервисов с таблицами монолита | Сохраняет связанность и блокирует database-per-service |
| Бесконечная поддержка legacy ACL | Увеличивает стоимость и риск; ACL должен иметь явный decommission date |

## Компромиссы

- Двойная запись/CDC на переходном этапе увеличивает нагрузку и стоимость.
- Сравнение ответов монолита и сервисов требует дополнительной автоматизации.
- Сохранение старых контрактов временно ограничивает качество новых API.
- Необходим явный процесс deprecation, иначе временная совместимость станет постоянной.

## Контроль завершения совместимости

Для каждого домена ведётся compatibility checklist:

- все клиенты `/v1` идентифицированы;
- метрики использования legacy endpoint собираются;
- владелец клиента подтвердил переход;
- выставлена дата отключения;
- после отключения legacy route удалён из Gateway;
- ACL и mapping-таблицы помечены к удалению.
