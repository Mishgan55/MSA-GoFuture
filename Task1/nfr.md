# Нефункциональные требования целевой архитектуры

## Контекст

НФТ служат входными ограничениями для декомпозиции. Они измеримы, привязаны к бизнес-целям и разделены на обязательный целевой уровень и промежуточный уровень стабилизации.

## 1. Производительность и пропускная способность

| Показатель | Целевое значение | Комментарий |
|---|---:|---|
| Конкурентные активные поездки | 500 000+ | Пиковое значение, а не среднесуточное |
| Входящие обновления геопозиции водителей | до 250 000 событий/с глобально | При активной поездке — обновление раз в 2–5 секунд |
| Создание заказа | p95 ≤ 500 мс в домашнем регионе | Не включая внешний платёжный ответ длительной операции |
| Расчёт тарифа/предложения цены | p95 ≤ 300 мс | Для заранее вычисленных зон и кешированных тарифов |
| API чтения состояния поездки | p95 ≤ 200 мс | Через read model/кеш, без цепочки межсервисных запросов |
| Подтверждение приёма location event | p95 ≤ 100 мс | Ingestion не должен ждать полной обработки |
| End-to-end задержка доменного события | p95 ≤ 2 с для critical events | От commit в сервисе-владельце до обработки ключевым потребителем |

## 2. Масштабируемость

| Требование | Целевое значение |
|---|---|
| Горизонтальное масштабирование stateless services | Автоматически по CPU, RPS, consumer lag и custom business metrics |
| Масштабирование location ingestion | Независимо от transactional booking core |
| Партиционирование высокочастотных потоков | По `region`, затем по `driver_id`/`booking_id`, чтобы сохранить порядок по сущности |
| Масштабирование БД | Вертикально ограничено; предпочтительны sharding/read replicas/partitioning |
| Региональное масштабирование | Не менее трёх production-регионов; добавление региона без изменения бизнес-кода |

## 3. Доступность и надёжность

| Показатель | Промежуточно, 2 месяца | Целевое значение |
|---|---:|---:|
| Availability критичных сервисов edge, booking, driver, pricing, payments | 99,9% | 99,95–99,99% |
| MTTR критичных инцидентов | ≤ 1 часа | ≤ 15 минут |
| RTO regional failover | ≤ 60 минут | ≤ 15 минут для критичных сценариев |
| RPO active trip/payment | ≤ 5 минут | 0–1 минута в зависимости от класса данных |
| Каскадные отказы | Допустимы только как инцидент с action plan | Не допускаются: bulkhead, timeouts, circuit breaker, backpressure |
| Деградация некритичных функций | Ручная | Автоматическая: notification/analytics/fraud enrichment могут временно отключаться |

Классификация критичности:

- **Tier 0:** API Gateway, IAM/AuthN, Booking, Driver Availability/Location, Pricing, Payments, event backbone.
- **Tier 1:** Notification, Geography, Fraud realtime scoring.
- **Tier 2:** Analytics, BI, отчёты, исторические read models.

## 4. Согласованность и целостность данных

| Класс данных | Модель согласованности |
|---|---|
| Платёжный ledger, финансовые операции, выплаты | Strong consistency внутри Payments; идемпотентные операции; запрет потерянных обновлений |
| Статус активной поездки | Strong consistency внутри Booking; состояние публикуется наружу событиями |
| Доступность и геопозиция водителя | Eventual consistency; допустимы пропуски устаревших обновлений |
| Тарифы и зоны | Strong consistency для справочников; cached/eventual reads для высоконагруженных сценариев |
| Аналитика и ML | Eventual consistency, но с проверяемым качеством и lineage |
| Уведомления | At-least-once доставка внутри платформы, deduplication перед внешним провайдером |

## 5. Безопасность и соответствие требованиям

- OIDC/OAuth 2.1 для пользовательских и сервисных аутентификаций; SAML/OIDC federation для партнёров.
- mTLS между сервисами в production service mesh.
- Принцип минимальных привилегий: каждый сервис имеет собственную БД-роль и secrets scope.
- Шифрование данных в передаче и хранении; региональные ключи KMS.
- Audit trail для действий администраторов, платежей, изменений тарифов и доступа к персональным данным.
- PII классифицируется и минимизируется в событиях; в Kafka публикуются идентификаторы и технические атрибуты, а не лишние персональные данные.
- Соответствие локальным требованиям резидентности данных, consent management, retention и праву на удаление там, где применимо.

## 6. Наблюдаемость и управляемость инцидентами

- Единые OpenTelemetry-трассы через edge, sync calls, Kafka consumers и внешние интеграции.
- Метрики RED для API: rate, errors, duration.
- Метрики USE для ресурсов: utilization, saturation, errors.
- Business metrics: активные поездки, match rate, время назначения водителя, cancellation rate, payment success rate.
- Корреляция логов по `trace_id`, `booking_id`, `driver_id`, `tenant_id` и `region`.
- Error budget policy для каждого Tier 0/Tier 1 сервиса.

## 7. Deployability и изменяемость

| Показатель | Целевое значение |
|---|---|
| Независимый деплой сервиса | Да, без координации релизов с другими доменами |
| Время сборки одного сервиса | ≤ 10–15 минут |
| Время rollback | ≤ 10 минут |
| Время выхода новой функции | ≤ 2 недели |
| Контрактные тесты | Обязательны для public API и event schema |
| Database migrations | Backward-compatible expand/contract, запрет destructive изменений в одном релизе |
| Feature flags | Для всех рискованных изменений и региональных rollout |

## 8. Совместимость и миграция

- Не ломать существующие мобильные клиенты минимум две major-версии после выделения сервиса.
- API versioning: `/v1`, `/v2`; deprecation policy не менее 90 дней.
- Поддержка смешанного режима, когда часть сценариев выполняется монолитом, а часть — сервисами.
- Переключение трафика через API Gateway и feature flags без изменения DNS мобильных приложений.
- Финальный cutover данных каждого домена: не более 5 минут недоступности соответствующего write path.

## 9. Стоимость и FinOps

- Автоматическое scale-to-demand для stateless workloads; запрет постоянного избыточного резервирования «на пик».
- Снижение инфраструктурных затрат за счёт autoscaling и правильного sizing минимум на 40% относительно ручного вертикального масштабирования монолита.
- Обязательные labels/tags по `service`, `team`, `environment`, `region`, `tenant`.
- Showback/chargeback для команд и партнёрских tenant workloads.

## 10. Ограничения

- Python/Django остаётся допустимым стеком для ряда сервисов на переходном этапе, но высоконагруженные streaming/stateful компоненты могут использовать Java/Kotlin и Flink.
- PostgreSQL остаётся основным transactional storage на первом этапе; замена СУБД допускается только по ADR отдельного домена.
- RabbitMQ сохраняется временно для legacy Celery-задач, но новая событийная платформа строится на Kafka.
