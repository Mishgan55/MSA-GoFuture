# Механизм геомаршрутизации пользователей

## Контекст

Пользователь должен попадать в ближайший работоспособный регион, но нельзя менять регион посередине активной поездки. Также нельзя полагаться только на географическую близость: резидентность данных и страна регистрации могут требовать конкретного региона.

## Выбранное решение

Применяется двухуровневая маршрутизация:

1. **Первичная маршрутизация через Route53 DNS**:
   - geolocation rules сначала определяют обязательный контур для стран с требованиями резидентности;
   - внутри разрешённой географической зоны latency/weighted rules выбирают ближайший здоровый регион;
   - health checks исключают нездоровый регион. Такая вложенная схема реализуется через Route53 Traffic Flow/alias-записи, а не через смешение несовместимых routing policies на одной записи.
2. **Region affinity после аутентификации**:
   - access token содержит `home_region` и `tenant_region` claims;
   - API Gateway проверяет соответствие региона;
   - если пользователь попал не в домашний регион, Gateway возвращает управляемый redirect/region hint или проксирует только безопасные read-only операции;
   - мобильный клиент сохраняет preferred endpoint до явного изменения home region.

## Поток первого входа

1. Клиент запрашивает `api.gofuture.com`.
2. Route53 определяет регион по latency/geolocation и health state.
3. Региональный API Gateway принимает запрос и вызывает локальный IAM/bootstrap service.
4. После регистрации/аутентификации пользователь закрепляется за домашним регионом.
5. В токене появляется `home_region`; дальнейшие запросы используют его.

## Поток активной поездки

- Все операции активной поездки выполняются только в регионе, где создана поездка.
- Если водитель/пассажир физически перемещается, это не меняет регион активной поездки.
- После завершения поездки домашний регион может быть пересчитан по правилам резидентности и продуктовой логике.
- Межрегиональные поездки обрабатываются как отдельные городские/региональные конфигурации, но не как миграция активного state во время поездки.

## Почему не только Global Accelerator/Anycast

AWS Global Accelerator уменьшает сетевую задержку за счёт anycast, но не выражает все правила резидентности и домашнего региона. Поэтому основной управляемый механизм — Route53 Traffic Flow с geolocation-first policy, latency/weighted target selection и application-level affinity. Global Accelerator может быть добавлен позднее как сетевой ускоритель перед региональными endpoint'ами, но не заменяет region affinity.

## Обработка отказа региона

1. Route53 health check определяет деградацию endpoint'а.
2. Новые пользовательские сессии направляются в ближайший здоровый разрешённый регион.
3. Для пользователей с домашним регионом в аварийном контуре применяется failover policy:
   - critical read-only режим, если DR replica доступна;
   - перенос write traffic после fencing и promotion replica;
   - ограничение неcritical функций до восстановления.
4. Активные поездки восстанавливаются из последней реплики/логов состояния с явным reconciliation.
5. После возвращения региона трафик возвращается постепенно через weighted routing.

## Требования к клиентским приложениям

- клиент обязан обрабатывать HTTP redirect/region hint и обновлять preferred endpoint;
- клиент не должен жёстко кешировать DNS надолго;
- для active trip клиент отправляет `trip_region` в запросе или получает его из booking state;
- offline/разрыв сети не должен приводить к самостоятельному выбору другого региона без подтверждения backend.

## Метрики

- DNS routing decisions по странам/регионам;
- доля запросов, попавших не в домашний регион;
- redirect rate;
- p95 latency по стране и региону;
- health check flapping;
- количество active trips в failover mode.

Схема представлена в [georouting.puml](./georouting.puml).
